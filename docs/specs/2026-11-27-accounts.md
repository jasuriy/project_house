## How it works

- **Accounts live in our database.** A password is never stored, only its argon2id hash (library
  `argon2-cffi` 25.1, default settings: 3 passes, 64 MiB, measured 29 ms per hash locally).
  Hashing runs in a worker thread (`asyncio.to_thread`) so it does not stall other requests, and
  at most 4 run at once (an `asyncio.Semaphore`): 20 parallel logins would otherwise need 1.28 GB.
- **Being logged in = a cookie.** After sign-up or login the API sets `ph_session`: a random 32-byte
  token, `HttpOnly` (page scripts cannot read it), `Secure`, `SameSite=Lax`, valid 30 days. The
  database keeps only the token's SHA-256, so a leaked database does not leak live sessions.
  Logout deletes the row.
- **Why a cookie works here:** the browser reaches the API through our own site (`/api/*`, forwarded
  by Next.js), so the cookie belongs to the site. Verified locally with `next dev`: the API's
  `Set-Cookie` reaches the browser and the browser's `Cookie` reaches the API, for GET and POST.
  Not yet verified on Vercel; first thing to check on the first deploy.
- **Sign up, log in and log out are browser calls** (`fetch` to `/api/v1/auth/*` from the page),
  never Server Actions or the server-side API client: a `Set-Cookie` answered to the Next.js
  server would stay on the server and never reach the browser.
- **Pages rendered on the server** (header, upload page guard) read only `ph_session` from
  `cookies()` and send just that to the API (GET only). With cacheComponents this part streams in
  behind a `<Suspense>` boundary.
- **Forged requests from other sites:** `SameSite=Lax` stops the cookie on cross-site POSTs; the API
  also refuses a state-changing request (POST, PUT, PATCH, DELETE) whose `Origin` is not our site.
  All state-changing requests come from the browser, which always sends `Origin` on them.
- **Guessing passwords:** after 10 failed logins for one email within 15 minutes, that email's
  login is refused for 15 minutes (counted in the database, so it holds across Modal containers).
  Each attempt is recorded and counted *before* the password is checked, so guesses sent at the
  same moment cannot all be checked before any is counted (tested with 12 at once).

## GitHub sign-in

1. "Continue with GitHub" -> `GET /api/v1/auth/github/start` -> redirect to GitHub (scope
   `read:user user:email`, a random `state` kept in a short cookie).
2. GitHub sends the person back to `/api/v1/auth/github/callback` on our site. The API checks
   `state`, swaps the code for a token (the client secret stays on the server), reads the GitHub
   user and their primary verified email.
3. An account linked to that GitHub user: log in. None: create one (avatar from GitHub; username
   from the GitHub login, lowercased and cut to 30 characters; if that is taken or reserved, `-2`,
   `-3`, ... is added).
4. **No automatic linking by email.** Emails are not confirmed yet (A2), so anyone could have
   signed up with someone else's address. If the GitHub email is already used by a password
   account, the person is asked to log in with the password instead. Otherwise whoever registered
   an address first could take over the real owner's GitHub sign-in.

Needs from Bek: two GitHub OAuth Apps (one for local, callback `http://localhost:3000/...`; one for
production, callback `https://projecthouse-pied.vercel.app/api/v1/auth/github/callback`), their client
id and secret added to the Modal secret `projecthouse-prod` (steps given when we get there).

## Data

```
users     id uuid pk, username text unique (lowercase), display_name text,
          email text unique (stored lowercase), password_hash text null (null: GitHub only),
          github_id bigint unique null, github_login text null, avatar_url text null, created_at
sessions  token_hash bytea pk, user_id -> users (delete cascade), created_at, expires_at
login_failures  email, failed_at        (for the 15-minute limit; old rows are pruned)
projects  + owner_id -> users            (null for the 2 existing projects until assigned)
```

- **Username:** 3-30 characters, lowercase letters, digits and hyphens; words the site uses are
  reserved (`new`, `login`, `signup`, `api`, `admin`, `settings`, `u`, `projects`).
- **Display name:** 1-60 characters, spaces at the ends trimmed.
- **Password:** at least 8 characters, at most 128; no "must contain a symbol" rules (NIST
  SP 800-63B recommends length over composition).

## API

| Method and path | What it does |
|---|---|
| `POST /api/v1/auth/signup` | name, username, email, password -> account + cookie |
| `POST /api/v1/auth/login` | email, password -> cookie |
| `POST /api/v1/auth/logout` | deletes the session, clears the cookie |
| `GET /api/v1/auth/me` | the logged-in user, or 401 |
| `GET /api/v1/auth/github/start`, `.../callback` | GitHub sign-in (above) |

- Render (`POST /projects`) and the upload links now need a session; the project gets
  `owner_id`. Anonymous visitors can still see the feed and every project page.
- The feed card and the project page show the owner's name and avatar instead of the fixed
  "Jasurbek" (D6 ends).

### Step 1 in detail

- **Code:** a new package `app/accounts/` laid out like `app/projects/`: `models.py` (User,
  Session, LoginFailure), `schemas.py`, `passwords.py` (argon2id in a thread, at most 4 at once),
  `service.py` (sign up, log in, log out, read the session), `router.py`, plus `current_user`
  and `optional_user` dependencies for steps 2 and 3. New dependency: `argon2-cffi==25.1.0`.
- **Migration 0006:** `users`, `sessions`, `login_failures`. `projects.owner_id` waits for step 3,
  where it is first used, so no unused column ships.
- **Origin check:** a middleware next to `no_store` in `main.py`. POST, PUT, PATCH and DELETE need
  `Origin` equal to the new setting `SITE_ORIGIN` (no default, like the other settings); a missing
  or different `Origin` gets 403 `origin_not_allowed`. It covers the existing upload and Render
  calls too. The cookie is `Secure` when `SITE_ORIGIN` starts with `https://`.
- **Login:** the same answer for an unknown email, a wrong password and a GitHub-only account
  (401 "Wrong email or password"); an unknown email is still hashed once so it takes as long. A
  success clears that email's failures and deletes the user's expired sessions.
- **`Me` is private:** it holds the email and is only for `/auth/me`. The feed, project pages and
  profiles (step 3) get their own public shape without the email.
- **Sign-up:** username and email lowercased, then checked; username pattern
  `^[a-z0-9][a-z0-9-]{1,28}[a-z0-9]$` (no hyphen at either end). A taken username or email answers
  409 (`username_taken`, `email_taken`); the unique constraints decide, so two sign-ups at once
  cannot both win. Saying "email taken" tells a visitor that the address has an account; every
  sign-up form does this, accepted.
- **Only browser calls change data** [V]: the Next.js server sends GETs only
  (`frontend/src/lib/server-api.ts`); the three POSTs are browser fetches (`frontend/src/lib/api.ts`).
  So the Origin check cannot block a call made by the Next.js server, which sends no `Origin`.
- **Memory:** a Modal container with no `memory=` gets a 128 MiB request and "can exceed this
  minimum if the worker has available CPU or memory"; no default hard limit is documented
  (modal.com/docs/guide/resources). 4 hashes at once (about 256 MiB) are not killed, so `web()`
  keeps no `memory=` (a higher request would raise the always-on bill).
- **Local runs:** `backend/.env` needs `SITE_ORIGIN=http://localhost:3000`, or the API does not
  start; open the site as `http://localhost:3000`.
- **Before deploy (Bek says yes to all of it at once):**
  1. add `SITE_ORIGIN=https://projecthouse-pied.vercel.app` to the Modal secret `projecthouse-prod`;
  2. `modal run modal_app.py::migrate` (0006), then `modal deploy modal_app.py`; the frontend does
     not change in this step;
  3. the gate writes one test account to the production database (one `users` row and its
     `sessions` row), which is deleted afterwards and checked gone.

  `SITE_ORIGIN` must be in the secret **before** `modal deploy`: it has no default, so without it
  the API does not start and the whole site, feed included, is down. Step 1 is committed before
  deploying, so a rollback is a clean redeploy of 067b6ee.
- **Gate, in this order** (through `https://projecthouse-pied.vercel.app`):
  1. In a real browser on the live site (Playwright), POST `/api/v1/uploads/video/url`: it only
     signs a link (no row, no R2 write). 200 proves the browser's own `Origin` survives Vercel.
  2. Sign up the test account: 201 with `Set-Cookie` (HttpOnly, Secure, SameSite=Lax); `/auth/me`
     200; log out; `/auth/me` 401. The cookie's attributes are read outside the page (Playwright's
     network response or `context.cookies()`, or curl): page scripts never see `Set-Cookie`.
  3. A POST with a foreign `Origin` (curl): 403.
  4. Bek deletes the test account in Neon's SQL editor (its session goes with it):

     ```sql
     DELETE FROM login_failures WHERE email = 'gate-check@example.com';
     DELETE FROM users WHERE username = 'gate-check';
     SELECT count(*) FROM users WHERE username = 'gate-check';                    -- 0
     SELECT count(*) FROM login_failures WHERE email = 'gate-check@example.com';  -- 0
     ```
- **Rollback:** if probe 1 fails, uploads are broken: redeploy the previous commit (067b6ee) at once,
  then fix the design. Redeploy from a `git worktree` of 067b6ee; the 0006 tables can stay, the
  old code ignores them.
- The test account is `gate-check` / `gate-check@example.com`, never Bek's own, so his real
  sign-up stays free.

## Known risks accepted for now

- Without email confirmation, someone can sign up with an address that is not theirs; the real
  owner then cannot use it until "Forgot password" exists (A2).
- Without "Forgot password", a forgotten password means a lost account.
- The login limit is per email, so anyone who knows an email can lock its owner out for 15 minutes
  by typing wrong passwords.
- (Accepted by Bek, 2026-11-27) Sign-up has no rate limit: a script can create many accounts.
- (Accepted by Bek, 2026-11-27) There is no per-address (IP) limit: logins with ever-new emails each cost one hash (about 30 ms of
  CPU), so a flood costs CPU and Modal money, and each such email leaves a `login_failures` row
  that is only removed when that same email is tried again.
